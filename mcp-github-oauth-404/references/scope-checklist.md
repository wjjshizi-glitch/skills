# GitHub OAuth Scope 最小权限检查

`scope` 决定 OAuth App 可代表用户访问的 GitHub 资源。scope 过宽通常**不会导致 404**，但应在授权前确认它与 MCP 的实际用途相称。

## 常见 scope

| Scope | 含义 | 风险提示 |
|---|---|---|
| `repo` | 对私有和公开仓库的广泛访问权限，具体能力取决于 GitHub OAuth 授权模型 | 范围很宽，应有明确业务理由 |
| `read:org` | 读取组织成员资格等组织信息 | 可能暴露组织结构 |
| `read:user` / `user:email` | 读取用户资料或邮箱 | 仅在身份识别确有需要时申请 |
| `public_repo` | 面向公开仓库的访问范围 | 对只需公开资源的功能通常更合适 |

## 审查清单

1. MCP 是否真的需要访问私有仓库？若否，避免 `repo`。
2. MCP 是否只读取数据？若是，确认产品没有申请与写操作不相称的权限。
3. 是否能将组织、邮箱等身份类 scope 拆分为按需授权？
4. 授权页面展示的 OAuth App 名称、发布者和业务入口是否一致？
5. scope 的 URL 编码前格式应为空格分隔，例如 `repo read:org read:user`。

如果 scope 与预期不符，取消授权并向产品/安全团队报告。不要尝试通过修改 scope 绕过应用的权限设计。
